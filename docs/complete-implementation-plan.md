# SentinelPulse Complete Implementation Plan

## 1. Goal

Complete every pending or partial requirement in the attached endpoint-monitoring checklist and bring SentinelPulse from a dashboard foundation to a verifiable end-to-end monitoring platform. The target architecture is **Endpoint Agent → Secure Ingestion → Durable Storage → Processing/Alert Engine → Live Dashboard/Reports**, with Windows-first delivery and a documented path for macOS/Linux parity.

This is a **planning document only**. No source files, database schemas, external services, production data, or deployment state will be changed until this plan is approved and the relevant human-in-the-loop gate is explicitly approved.

## 2. Success Criteria

The project will be considered complete only when all of the following evidence exists:

| Area | Completion evidence |
|---|---|
| Agent inventory | A Windows agent can collect OS, boot/uptime, user/timezone, CPU, RAM, GPU, motherboard, BIOS, serial/asset, disks, battery, network, and permitted peripheral data. Unsupported hardware fields are represented as explicit `null`/`unknown` values rather than fabricated values. |
| Resource monitoring | Current and historical CPU, per-core CPU, RAM, disk I/O, network, GPU, battery, and system uptime metrics are ingested with timestamps, endpoint identity, schema version, and collection status. |
| Applications/processes | Installed application inventory and process/application telemetry include the requested fields: installation metadata, CPU/RAM/disk/network consumption, start time, process status, usage duration, launch count, and last-used time where the OS permits. |
| Backend | Device registration, authentication, heartbeat, telemetry ingestion, idempotency, retry/backoff, durable dead-letter handling, alert evaluation, stale-device detection, and live event publication are implemented with persistent state. |
| Data model | Relational and time-series schemas are synchronized through reviewed migrations. No destructive migration is executed without explicit approval and a backup/rollback plan. |
| Dashboard | Device list, details, hardware, performance, applications, usage, alerts, reports, groups/tags, locations/departments/ownership, maintenance mode, health score, and live updates are connected to real API contracts. |
| Reports | CSV and actual PDF files are generated by backend endpoints, authenticated, downloadable, and covered by content and permission tests. |
| MSI | A Windows-native CI runner can compile a versioned WiX v4 MSI, install it, verify the Windows Service, run a smoke test, uninstall it, publish a checksum, and expose a controlled artifact/download workflow. |
| Validation | TypeScript, unit, integration, migration dry-run, API contract, security, build, MSI, and visual checks pass. Windows-specific evidence is recorded separately from Linux sandbox evidence. |
| Operations | Logs, metrics, retry visibility, dead-letter inspection, audit events, release version history, and rollback procedures are documented. |

## 3. Current Known Gaps

The repository currently has a dashboard foundation, managed authentication/database scaffolding, hardware UI extensions, an SSE route scaffold, agent code references, WiX source, and documentation. The following items remain unverified or incomplete and must not be marked complete merely because a UI control or source template exists:

1. Extended telemetry needs matching database queries, tRPC/API procedures, ingestion persistence, and agent payload integration.
2. SQLite buffering requires encrypted payload storage, dequeue/replay, acknowledgement, retention, corruption recovery, and Windows validation.
3. MSI generation requires actual Windows-native compilation, artifact storage, status polling, download authorization, checksums, signing policy, install verification, and rollback behavior.
4. Ingestion must replace in-memory or simulated state with durable persistence, idempotency records, retry policies, dead-letter storage, and heartbeat processing.
5. Alerting needs a real worker or scheduled processing loop for threshold breaches and stale check-ins.
6. CSV/PDF reports need real authenticated file responses, not a button, HTML placeholder, or fabricated URL.
7. Drizzle schema and SQL migration files must be generated, reviewed, applied only with approval, and checked for synchronization.
8. Test coverage must include the new paths rather than relying only on the existing small unit suite.

## 6. Phase-Wise Implementation Plan

### Phase 0 — Goal, prerequisites, and audit

Read the attached checklist and current repository without mutating project or external state. Inventory existing schemas, types, routes, agent projects, packaging files, report utilities, test suites, environment variables, and current TODOs. Create an evidence matrix mapping every requirement to its current status: `complete`, `partial`, `scaffold`, `missing`, or `blocked by environment`.

**Gate:** The matrix must name the exact file, route, test, or external validation needed for every requirement. Ambiguities become explicit assumptions, not silent implementations.

### Phase 1 — Contracts and data model

Define versioned telemetry envelopes and schemas. Every envelope must include `schemaVersion`, `endpointId`, `agentVersion`, `collectedAtUtc`, `sequenceNumber`, `idempotencyKey`, collection duration, and per-module error/unsupported status. Split inventory snapshots from time-series samples. Use UTC timestamps and typed nullable fields for hardware unavailable on a device.

Add relational tables for endpoint metadata, organization membership, device groups/tags/departments/locations/ownership, hardware snapshots, disks, network adapters, peripherals, installed apps, alert rules, alerts, notification destinations, agent releases, MSI artifacts, heartbeats, idempotency records, dead letters, and audit events. Add time-series tables/hypertables for CPU/RAM/disk/network/GPU/battery/process/application-usage metrics.

Define procedures/routes for inventory, heartbeat, telemetry ingestion, endpoint detail, application usage, health score, metadata management, report generation, MSI build status, MSI download authorization, alert acknowledgement, rule management, and live events.

**Gate:** Generate migration SQL and API type checks in a disposable environment. No production database change is allowed at this stage.

### Phase 2 — Windows agent and secure local buffering

Implement the .NET agent as a Windows Worker Service with modular collectors:

| Collector | Main responsibilities |
|---|---|
| OS | Version/build, architecture, hostname/device ID, boot time, uptime, last reboot, logged-in user, timezone, patch state. |
| CPU | Model, cores, threads, current/max clock, total/per-core utilization, temperature where supported. |
| Memory | Total, used, available/free, committed memory, utilization. |
| GPU | Model, VRAM, utilization, temperature where supported. |
| Storage | Physical model/type, logical volumes, capacity/free/used, health, SMART, I/O, temperature where supported. |
| Battery | Charge, design/full capacity, health, charging state, cycles, remaining time, AC/battery mode, temperature where supported. |
| Network | Adapter, IP, MAC, gateway, DNS, SSID, signal, upload/download, latency, packet loss, VPN, connection history. |
| Peripherals | PnP devices, monitors, USB/Bluetooth devices where OS APIs expose safe inventory. |
| Applications/processes | Installed software and process metrics with privacy-safe fields only; no keystrokes, passwords, message contents, or arbitrary screen capture. |

Implement a SQLite queue with encrypted payloads using Windows DPAPI scoped to the service account or machine policy. Add enqueue, dequeue, retry count, next-attempt time, acknowledgement deletion, dead-letter transition, retention cleanup, corruption handling, and bounded disk usage. Use atomic transactions so a process crash cannot lose or duplicate a record. Add a deterministic fake transport for offline tests.

**Gate:** Windows runner tests must prove encryption/decryption, restart recovery, replay ordering, acknowledgement, retry exhaustion, retention, and service start/stop. Linux cannot substitute for DPAPI or Service Control Manager evidence.

### Phase 3 — Durable ingestion and processing

Implement the ingestion API with strict payload validation and a durable transaction boundary. The sequence is:

```text
Receive HTTPS request
→ authenticate endpoint credential/certificate
→ validate schema and size limits
→ check idempotency record
→ persist raw envelope or durable queue record
→ acknowledge only after durable write
→ process asynchronously
→ update endpoint heartbeat and inventory
→ write time-series samples
→ evaluate alert rules
→ publish live event
→ mark processing result or dead-letter with reason
```

Use bounded exponential backoff with jitter for transient downstream failures. Persist idempotency keys with endpoint scope and expiry. Never use a process-local `Set` as the source of truth. Record retry attempts, last error, next attempt, and dead-letter reason. Add backpressure and rate limits per endpoint/organization. Handle malformed payloads separately from retryable infrastructure failures.

Add a heartbeat monitor that marks devices stale based on policy, emits one deduplicated alert per outage, and resolves it after a valid check-in. Add alert evaluation for CPU, RAM, disk free/health, battery health, high network usage, app crashes, missing OS updates, agent stopped, and check-in timeout.

**Gate:** Integration tests must simulate timeout, duplicate delivery, process restart, queue outage, database outage, malformed data, and recovery without data loss or duplicate alerts.

### Phase 4 — Live transport and dashboard integration

Expose an authenticated SSE or WebSocket stream with tenant/role/endpoint authorization. Send `telemetry_updated`, `inventory_updated`, `heartbeat_changed`, `alert_opened`, `alert_resolved`, and `agent_status_changed` events. Add connection limits, heartbeat frames, reconnect backoff, last-event replay or a clear resynchronization path, and redaction of sensitive payloads.

Wire dashboard queries to typed procedures and the live stream. Replace local random updates in production mode. Keep a clearly labeled preview mode only when no backend/agent is available. Add loading, stale, disconnected, permission-denied, unsupported, and error states.

Add dashboard pages/tabs for performance, CPU per-core, memory, disk I/O, network, GPU, battery, system uptime, installed apps, running apps, app usage, groups/tags, device metadata, health score, alerts, notifications, reports, and agent releases.

### Phase 5 — Reports, health scoring, management, and notifications

Implement server-side CSV and PDF generation from authorized query results. Stream or stage files instead of loading unbounded fleet data into memory. Include report parameters, generated-at UTC timestamp, organization scope, and a stable report ID. Protect downloads with authorization and expiring URLs. Test empty datasets, large datasets, invalid date ranges, and unauthorized endpoints.

Define a versioned health-score formula with component scores and explainable deductions. Store the score inputs and formula version so historical scores remain reproducible. Add device groups, tags, departments, locations, assigned users, ownership, asset IDs, agent version, maintenance mode, remote configuration policy, and audit history.

Implement notification adapters for dashboard, email, Slack/Teams, webhook, and push only behind configured connectors. Use an outbox pattern so alert creation is not coupled to external delivery success. Record delivery attempts and suppress duplicate notifications.

### Phase 6 — MSI release and deployment workflow

Build a Windows-native release pipeline that:

1. Reads a signed release tag and converts it to a valid MSI numeric version.
2. Restores and builds the .NET agent in Release mode.
3. Publishes self-contained `win-x64` output.
4. Compiles WiX v4 source with the publish directory and version variables.
5. Validates MSI existence, size, ProductCode/ProductVersion, and SHA-256 checksum.
6. Installs silently on a clean runner and verifies the `SentinelPulseAgent` service, configuration directory, ACLs, startup mode, and log path.
7. Runs an offline agent smoke test and confirms buffering/heartbeat behavior.
8. Uninstalls and verifies service/file cleanup.
9. Uploads MSI, checksum, SBOM, test logs, and release metadata to approved artifact storage.
10. Exposes an authenticated dashboard release list with build status, version, checksum, and download authorization.

A Linux sandbox may generate source and CI definitions, but it cannot claim a working MSI without Windows-runner evidence. Signing is a separate protected gate and requires a user-approved certificate/signing environment.

### Phase 7 — Migration, testing, rollback, and release

Run schema generation and review the diff. Apply migrations only to an isolated development database after explicit approval. Capture a backup/state identifier and a rollback script before any non-destructive migration. Do not run `DROP`, destructive rewrite, production migration, cloud deployment, external notification, or certificate signing without a separate approval.

Test layers:

| Layer | Required tests |
|---|---|
| Unit | Collector parsing, nullable/unsupported fields, score calculation, retry policy, idempotency, report formatting, RBAC. |
| Contract | Payload validation, API response schemas, version compatibility, event types. |
| Integration | Ingestion → persistence → alert → live event → dashboard query; duplicate/retry/restart/recovery cases. |
| Database | Migration dry-run, indexes, constraints, retention, tenant isolation, time-series query performance. |
| Windows | Agent service lifecycle, WMI adapters, DPAPI, SQLite replay, WiX install/uninstall, MSI upgrade/downgrade. |
| Security | Credential rejection, tenant isolation, role restrictions, artifact authorization, report authorization, secret scanning. |
| Visual | Dashboard live, stale, empty, error, disconnected, unsupported, and large-data states. |
| Performance | Batch ingestion, backpressure, concurrent endpoints, report limits, live subscriber limits. |

If a test fails, stop the phase, record the failure in the action log, return to the design/pseudo-code for the affected module, revise implementation, rerun the failing test and all dependent tests, and only then advance.

## 7. Pseudo-Code and Self-Reflection

### Telemetry ingestion

```text
function ingest(envelope, credential):
    authenticate credential and endpoint scope
    reject payload when schema, size, timestamp, or tenant checks fail
    if idempotency key already has terminal success:
        return the original accepted result
    persist idempotency key as in-progress atomically
    write envelope to durable queue/raw table
    if durable write fails:
        do not acknowledge; return retryable error
    return accepted

worker loop:
    claim next durable envelope with lease
    validate and normalize nullable fields
    write inventory and time-series records in a transaction
    update heartbeat and stale state
    evaluate alert rules and outbox notifications
    publish authorized live event
    mark idempotency key complete
    on retryable error: increment attempt and schedule jittered retry
    on permanent error or exhausted retries: write dead-letter record
```

### Offline buffer

```text
collect payload
→ serialize canonical JSON
→ encrypt with DPAPI
→ transactionally enqueue with sequence and retry metadata
→ attempt upload in order
→ on accepted response, delete acknowledged row
→ on transient failure, retain and reschedule
→ on permanent failure, move to dead-letter
→ enforce retention and disk quota
```

### MSI release

```text
parse release tag
→ validate semantic and MSI numeric versions
→ publish agent
→ compile WiX source
→ validate artifact metadata/checksum
→ install MSI on clean Windows runner
→ verify service and offline smoke test
→ uninstall and verify cleanup
→ upload artifact and logs
→ expose authorized download
```

The design favors durable state and explicit acknowledgement over optimistic UI updates because endpoint telemetry and release artifacts must not be silently lost. It also keeps collectors modular so unsupported hardware can degrade per module without dropping the entire envelope.

## 8. Human-in-the-Loop Approval Gates

The following exact actions require explicit user approval immediately before execution:

| Gate | Approval required before |
|---|---|
| A | Applying any migration to a real database, even if described as non-destructive. |
| B | Running any `DROP`, `DELETE`, destructive schema rewrite, data backfill, or production database write. |
| C | Deploying or changing external infrastructure, cloud resources, queues, artifact storage, DNS, or webhooks. |
| D | Creating or using MSI signing certificates, publishing signed releases, or distributing an installer outside the test runner. |
| E | Sending real email, Slack, Teams, push, or webhook notifications. |
| F | Running a Windows self-hosted runner against a domain, enterprise hardware, or real endpoint fleet. |

Before each gate, the execution phase must show the exact command, target environment, expected side effects, backup/rollback plan, and validation command, then ask: **“Do you approve this action? (Yes/No)”**. Until the user replies `Yes`, only read-only inspection and local non-destructive tests may proceed.

## 9. Action Log Requirements

Maintain `docs/action-log.md` with one append-only entry per action:

```text
UTC timestamp | phase | action | files/commands | result | validation evidence | rollback/state reference
```

A failed action must include the error, affected files, attempted rollback, and the next loop-back phase. The log must never claim Windows, production, external-infrastructure, or MSI evidence that was not actually produced.

## 10. Assumptions and Open Risks

The initial implementation target is Windows x64 with .NET 8 and WiX v4. macOS/Linux parity is planned as adapter interfaces and later native agents, not silently represented as Windows support. Some telemetry such as temperature, battery cycles, SMART attributes, Wi-Fi signal, and per-process network usage is hardware/driver/API dependent; unsupported values must be recorded as unavailable with a reason.

The current managed web environment may not expose a production PostgreSQL/TimescaleDB, Redis, Windows SDK, WiX compiler, DPAPI, or Windows Service Control Manager. Those capabilities must be validated in the appropriate isolated runner. MSI signing, artifact distribution, external notifications, and production database migration remain blocked until the relevant human approval and credentials are available.

No requirement is considered complete merely because it has a type, UI placeholder, source template, fabricated URL, random sample, or documentation entry. Completion requires an executable code path and a matching validation artifact.

## 11. Execution Order After Approval

After this plan is approved, execute phases in order, with a checkpoint at the end of every phase. The first implementation phase should be the contracts/schema layer, not the UI. For every phase, use the loop **inspect → plan/pseudo-code → implement → self-review → isolated test → ground-truth validation → checkpoint**. If any validation fails, return to the affected plan/pseudo-code phase and do not advance.
